# Phase 13.54 — Vitamin Brand Successor and Decision Lineage

## Objective

Adopt the governed Vitamin Brand Foundation in the active Matching v2 queue without discarding or
silently reinterpreting the platform owner's completed attribute-evidence decisions.

## Decision classes remain separate

The successor protocol distinguishes three records:

- a product-pair candidate generated by the deterministic engine;
- a human decision about source-bound attribute evidence; and
- a final human product-match decision.

Brand enrichment does not authorize a match. This phase carries only compatible attribute-evidence
decisions. It does not inherit AI recommendations, launch paid AI review, create a final match,
release a gold set, or publish reporting.

## Fail-closed compatibility gate

An administrator must name the exact predecessor queue. Inside the same transaction that imports
the immutable successor, every latest attribute-evidence decision is reconciled against its
successor product pair. Carry-forward is allowed only when all of these remain unchanged:

- Product Pack identity, version, and certification-policy checksum;
- benchmark and competitor listing identities;
- Product Pack attribute and listing side;
- current attribute value and its evidence source;
- normalized proposed value;
- source image and visible label evidence;
- originating AI output checksum; and
- original proposal checksum.

The source image must still be present on both the predecessor and successor version of the same
listing. The original proposal document remains immutable. The successor decision preserves the
reviewer and verdict, adds an explicit carry-forward rationale, and supersedes the predecessor
decision. If one selected decision fails any check, the complete queue insert rolls back.

## Authority and cost boundary

The imported queue remains non-authoritative until every product relationship has a final human
outcome and a separate checksum-bound gold-set release and governed replay pass publication trust
gates. Queue succession makes no MetricsCart or OpenAI request and does not mutate Search, PDP,
image, AI, review, or reporting history.

## Verification

- Request validation requires an explicit predecessor whenever attribute evidence is carried.
- Brand-only case enrichment is compatible when the governed attribute evidence remains exact.
- Changed attribute values, removed source images, changed policy checksums, malformed proposal
  checksums, and missing product pairs fail closed.
- The focused Matching v2 API suite passes before deployment.

Production import and reporting outcomes are appended only after their checks complete.
